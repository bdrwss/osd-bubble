## 1. 核心技术挑战

在选框架之前，先明确这个项目的技术难点——它们直接决定选型权重：

| # | 挑战 | 难度 | 说明 |
|---|------|------|------|
| C1 | 全局键鼠钩子 | ★★★★ | 需在任意应用前台时捕获输入事件；Windows 用 `SetWindowsHookEx`，macOS 用 `CGEventTap`，均需原生 API |
| C2 | 透明 + 置顶 + 点击穿透窗口 | ★★★ | 气泡窗口必须 TopMost、背景全透明、鼠标事件穿透到下层应用 |
| C3 | 极低延迟（≤50 ms） | ★★★ | 从系统钩子回调到气泡渲染完成，整条链路需控制在 50 ms 内 |
| C4 | 极低资源占用 | ★★★ | 常驻后台工具，CPU ≤0.5%、内存 ≤60 MB 是验收线 |
| C5 | 跨平台（Win + macOS） | ★★★ | 两套系统的钩子 API、窗口模型、权限体系完全不同 |
| C6 | DPI / 多显示器 | ★★ | 气泡在不同缩放率的屏幕上保持清晰、位置正确 |
| C7 | 小体积分发 | ★★ | 教学工具面向非技术用户，安装包最好 < 30 MB，免安装绿色包更佳 |

**选型权重排序：C1 = C4 > C3 > C2 > C5 > C7 > C6。**

全局钩子和资源占用是"能不能做"的问题；延迟和窗口行为是"好不好用"的问题；其余是锦上添花。

## 4. 各方案详细评析

### A. Tauri 2（推荐）

**优势：**
- Rust 后端天然适配系统级编程：`SetWindowsHookEx`、`CGEventTap` 可通过 `windows-rs` / `core-graphics` crate 直接调用，无需额外 FFI 桥接层。
- 资源占用极低，无内置浏览器引擎（使用系统 WebView2 / WKWebView），空闲 CPU < 0.3%，内存 40–80 MB，满足验收标准。
- 安装包 3–15 MB，适合教学工具"小而美"定位；支持 NSIS / MSI / DMG / AppImage 多格式打包。
- 前端用 HTML/CSS/JS 写设置界面，开发效率高，UI 表现力强。
- 官方支持 Windows / macOS / Linux 三端，代码复用率高。
- 内置自动更新、系统托盘、全局快捷键等插件。

**风险与对策：**

| 风险 | 影响 | 对策 |
|------|------|------|
| WebView2 多显示器 DPI 缩放偶有模糊 | 气泡在副屏可能不够锐利 | 气泡窗口独立于主 WebView，用原生窗口 + 自绘（见架构设计） |
| Rust 学习曲线（团队若无 Rust 经验） | 开发速度前期偏慢 | 钩子层代码量有限（~500 行），可参考 `rdev` / `inputbot` 开源实现 |
| macOS 辅助功能权限引导 | 用户首次需手动授权 | 内置权限检测 + 引导弹窗，参考 KeyCastr 流程 |
| WebView 渲染延迟（~16 ms） | 叠加钩子延迟可能逼近 50 ms | 气泡渲染走原生层（见下），不经过 WebView |

### B. Electron

**优势：** 生态最成熟，透明窗口 + 点击穿透方案文档丰富；前端开发者零门槛；Chromium 对 DPI/多屏处理最完善。

**致命短板：** 内存基线 200 MB+、安装包 120 MB+，与"轻量教学工具"定位严重冲突。在教室机房（通常 4–8 GB 内存）上常驻一个 Electron 进程，资源观感很差。全局钩子仍需通过 napi-rs 桥接 Rust/C++，并未省去原生开发工作量，反而多了一层。

**结论：不推荐。** 除非团队只有前端开发者且对体积/内存无要求。

### C. Flutter Desktop

**优势：** Skia 自绘渲染延迟低（~8 ms），动画表现力好；Hot Reload 开发体验佳。

**短板：** 桌面端透明 + 穿透窗口方案不稳定（社区 issue 长期未关闭）；全局钩子需写 Platform Channel 插件，Dart 侧无法直接调系统 API；高 DPI 缩放历史问题多；桌面生态（托盘、自启、更新）依赖社区插件，成熟度不足。

**结论：不推荐用于本项目。** 更适合强交互 UI 应用，不适合"系统级常驻小工具"。

### D. Qt (QML + C++)

**优势：** 性能最优之一，C++ 直接调系统 API；窗口透明/穿透/置顶方案成熟（`WA_TranslucentBackground` + `WindowTransparentForInput`）；跨平台历史悠久。

**短板：** C++ 开发效率低于 Rust/Go（内存管理、编译速度）；商业授权费用（GPL 或商业二选一）对独立开发者有门槛；QML 写设置界面可以但生态不如 Web；打包体积 20–80 MB 尚可但不够极致。

**结论：可行但非最优。** 若团队有 C++/Qt 经验，是稳妥选择；否则 Rust 方案更现代。

### E. 原生双端（C#/WPF + Swift/AppKit）

**优势：** 性能天花板最高；窗口行为控制最精确；Carnac（C#/WPF）和 KeyCastr（ObjC/Swift）已验证此路线可行。

**短板：** 两套代码、两套构建、两套测试，开发维护成本翻倍；功能迭代需双端同步；无法复用 UI 代码。

**结论：适合"只做单平台"或"已有双端团队"的情况。** 对小团队/独立开发者，跨平台框架更务实。

### F. Wails (Go + Web)

**优势：** 与 Tauri 思路相同（Go 后端 + 系统 WebView），Go 学习曲线比 Rust 平缓；打包体积小。

**短板：** Go 调用系统 API 需 CGo，跨平台编译体验差（尤其 macOS 交叉编译）；全局钩子相关 Go 库生态薄弱（`robotgo` 维护不活跃）；CGo 调用开销在高频钩子回调中可能成为瓶颈。

**结论：可行但生态支撑不如 Tauri。** 若团队是 Go 背景可考虑。

## 5. 最终推荐

### 推荐方案：Tauri 2 + Rust（后端）+ Web（设置界面）

**核心理由（按权重排序）：**

1. **全局钩子能力（C1）：** Rust 是系统级编程的最佳现代语言，`windows-rs` 和 `core-graphics` 提供零成本抽象，无需额外桥接层。
2. **资源占用（C4）：** 无 Chromium 负担，空闲内存 40–80 MB、CPU < 0.3%，在教室低配机器上无存在感。
3. **体积（C7）：** 安装包 < 15 MB，可进一步做便携版（单 .exe < 10 MB）。
4. **跨平台（C5）：** 官方三端支持，一套代码覆盖 V1.0 的 Windows + macOS。
5. **开发效率：** 设置界面用 Web 技术快速迭代；Rust 钩子层代码量有限，不需要写大量 Rust。

### 推荐架构

```
┌─────────────────────────────────────────────────┐
│                  Tauri 2 Shell                   │
├─────────────────────────────────────────────────┤
│  Rust Core（主进程）                             │
│  ┌───────────┐  ┌───────────┐  ┌────────────┐  │
│  │ Input     │  │ Overlay   │  │ Settings   │  │
│  │ Hook Mgr  │──│ Window    │  │ & State    │  │
│  │           │  │ (原生窗口) │  │            │  │
│  └─────┬─────┘  └───────────┘  └────────────┘  │
│        │              ▲                         │
│        │   按键事件    │  渲染指令               │
│        └──────────────┘                         │
├─────────────────────────────────────────────────┤
│  WebView（设置面板，按需打开）                    │
│  HTML + CSS + JS / 轻量框架（Svelte/Solid）      │
└─────────────────────────────────────────────────┘
```

**关键设计决策：气泡渲染不走 WebView，走原生窗口。**

理由：WebView 渲染有 ~16 ms 帧延迟，叠加 IPC 开销可能逼近 50 ms 上限。改为 Rust 直接创建一个小型原生窗口（Windows 用 `CreateWindowExW` + `WS_EX_LAYERED`；macOS 用 `NSPanel`），用 GPU 加速的 2D 绘制（`tiny-skia` 或 `softbuffer`）画气泡，延迟可压到 < 5 ms。

WebView 仅用于设置面板（低频交互），不影响主链路性能。

### 关键 Crate / 库选型

| 职责 | 推荐库 | 备选 |
|------|--------|------|
| 全局键鼠监听 | `rdev`（跨平台，活跃维护） | `inputbot`、手写 `windows-rs` |
| 原生透明窗口 | `windows-rs` + `WS_EX_LAYERED` / `cocoa` + `NSPanel` | `winit`（跨平台窗口抽象） |
| 2D 气泡绘制 | `tiny-skia`（纯 Rust，CPU 光栅化） | `softbuffer` + 手动像素、`raqote` |
| 动画/计时 | `std::time` + 自绘帧循环 | `tokio`（若需异步） |
| 设置持久化 | `serde` + `serde_json`（JSON 配置文件） | `toml` |
| 系统托盘 | `tauri-plugin-tray` | `tray-icon` |
| 自动更新 | `tauri-plugin-updater` | — |
| 前端框架（设置面板） | Svelte 5（轻量、编译型） | Solid.js、Preact |

## 6. 技术验证计划（PoC）

在正式开发前，建议用 3–5 天完成以下验证：

| 阶段 | 目标 | 验收标准 | 预计耗时 |
|------|------|----------|----------|
| PoC-1 | Windows 全局键盘钩子 | 在任意应用中按键，Rust 回调能收到事件并打印 | 0.5 天 |
| PoC-2 | 原生透明穿透窗口 | 创建一个置顶、透明、鼠标穿透的小窗口，用 tiny-skia 画一个圆角矩形 | 1 天 |
| PoC-3 | 端到端延迟测量 | 钩子回调 → 窗口显示，计时 < 20 ms | 0.5 天 |
| PoC-4 | macOS 权限 + CGEventTap | 辅助功能授权后，能捕获键盘事件 | 1 天 |
| PoC-5 | 多显示器 + DPI | 在 150% 缩放副屏上，气泡位置正确、文字清晰 | 0.5 天 |

**PoC 通过标准：** 5 项全部达标 → 进入 V1.0 开发；任一失败 → 评估 Qt 或原生方案作为 Plan B。

## 7. 风险登记簿

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| WebView2 在 Win10 旧版本缺失 | 中 | 设置面板无法打开 | 安装包捆绑 Evergreen Bootstrapper；或设置面板改用原生对话框 |
| macOS App Store 审核拒绝（全局钩子） | 高 | 无法上架 MAS | 走独立分发（DMG + 公证），不上 MAS |
| 杀毒软件误报（全局钩子行为） | 中 | 用户安装受阻 | 代码签名（EV 证书）；提交白名单申请；提供安装说明 |
| Rust 团队经验不足 | 中 | 前期开发慢 | 钩子层参考 `rdev` 源码；设置面板全用 Web 技术降低 Rust 用量 |
| 高频输入（>30/s）下渲染丢帧 | 低 | 气泡显示不全 | 输入合并（100 ms 窗口）+ 渲染帧率锁 60 fps |

## 8. 与竞品的技术路线对照

| 产品 | 平台 | 技术栈 | 体积 | 局限 |
|------|------|--------|------|------|
| Carnac | Windows | C# / WPF / ReactiveUI | ~5 MB | 仅 Windows；不支持鼠标；项目已停止维护 |
| KeyCastr | macOS | Objective-C / AppKit | ~2 MB | 仅 macOS；不支持鼠标；UI 定制性弱 |
| NohBoard | Windows | C# / WinForms | ~3 MB | 仅键盘；固定位置显示（非跟随光标） |
| 本工具（目标） | Win + Mac | Rust + Tauri 2 | < 15 MB | — |

差异化优势：跨平台统一体验、鼠标+键盘全覆盖、气泡跟随光标、面向教学场景的配置预设。
